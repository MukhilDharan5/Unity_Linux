# Architecture

The daemon owns device identities, sessions, trust, feature negotiation, incoming phone state, transfer quarantine, and asynchronous operations. It publishes only the public API. `unityctl`, GTK, and future clients consume that API. No frontend is needed for reconnection, incoming events, or receiving files. D-Bus service activation and a systemd user unit are provided independently of the desktop entry.

The Rust workspace has eight crates. The GTK directory intentionally uses Python/PyGObject: Fedora already provides GTK4/libadwaita introspection, the client needs no native protocol implementation, and its dependencies stay entirely outside the Rust service graph. Android uses native Kotlin and platform APIs with no cross-platform GUI or network SDK. All Android feature handlers are separate modules behind `Feature` and `FeatureRegistry`.

`unity-protocol` defines tagged JSON messages. `unity-transport::Transport` hides sockets from the core; bounded queues and framed messages provide backpressure. LAN and Bluetooth Classic RFCOMM both carry pinned TLS and the same device challenge authentication. The selector prefers Bluetooth for control and LAN for bulk when both are offered; RFCOMM also supports bulk data. Android defaults to maintaining both configured connections; Settings also provides single-transport modes. Linux registers three authenticated BlueZ server profiles with automatic RFCOMM channel allocation, independent control/audio/screen descriptors, sender verification and restart recovery. Audio routing uses PulseAudio/PipeWire monitor capture and Android AudioTrack playback; screen sharing uses JPEG streams. See [Bluetooth setup and validation](bluetooth.md) and [audio routing](audio-routing.md).

The Linux listener accepts private, loopback, and link-local peers. IPv4 LAN is the default. It uses rustls with a persistent certificate. Android pins that certificate before transmitting application messages. Explicit pairing issues a random per-device secret over TLS. Each later session proves possession using an unpredictable server challenge and HMAC-SHA256. This authenticates the phone; the pinned TLS certificate authenticates the computer. The server closes the initial pairing connection and requires a fresh authenticated session.

A live authenticated session is maintained per device and transport, so Bluetooth and LAN coexist. A replacement cancels only the previous session of the same transport. Small events and control commands prefer Bluetooth; files, photo previews, browsing, audio and screens prefer LAN. New work falls back to the surviving link. Every operation and transfer stays bound to its selected session generation; interrupted work fails and may be explicitly retried without replaying commands or continuing partial files on a different connection. There can be multiple devices and D-Bus clients concurrently. The daemon uses two Tokio workers. Idle sessions block on I/O, with 30-second heartbeat messages and a 90-second inactivity limit. Initial TLS and hello/auth steps have timeouts. Android independently authenticates, heartbeats and reconnects each transport with exponential backoff capped at 64 seconds plus jitter. First-time pairing is serialized, and both links subsequently use the same pinned desktop identity and phone credential. LAN availability changes publish state; OS socket failure triggers reconnection. There is no recurring Bluetooth scan or automatic hotspot/Wi-Fi Direct creation.

Losing one link cancels its incomplete transfers, pending operations and side streams while preserving the other link and cached phone state. Live state clears when the final link disconnects. Explicit disconnect closes both links. Trusted identities and feature toggles persist. Revocation deletes the saved credential and cancels both active sessions. Client grants are scoped to a unique D-Bus connection and disappear when its owner disconnects. Finished operation history expires after ten minutes when subsequent operations are submitted; the bounded history is limited to 512 objects.

Events are validated before entering the feature state cache. Notifications are maintained by notification ID, with an upper bound of 200 entries. Transfers stream in 48 KiB chunks with size and SHA-256 checks, never peer-controlled paths. Private incoming files stay under the daemon's state directory. Large command bodies and frames have separate bounds. The GTK client refreshes state in response to signals and coalesces changes using an idle callback; the CLI waits on operation signals.

GTK uses `Adw.NavigationSplitView`, `Adw.PreferencesPage`, groups, action/entry/switch rows, asynchronous Gio calls, and native file/confirmation dialogs. It displays actual device capabilities and disables unavailable actions. No phone sockets, Bluetooth calls, or Android-specific hardware handling exist in the frontend.

The installed frontend starts through a CLI launcher that grants access only to its verified child PID using the same public D-Bus approval API. GTK waits for its own approval status before requesting private snapshots, clears private views on revocation, and requests again after daemon restart. The launcher waits on signals and child exit; it performs no polling and adds no GTK dependency to Rust. Other clients retain the documented explicit approval flow.

No privileged helper exists yet because the implemented functions do not require one. Future network configuration and input injection into the Linux desktop must use narrowly scoped services or portals rather than elevating `unityd`.
