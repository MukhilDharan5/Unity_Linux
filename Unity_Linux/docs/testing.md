# Tests and evidence

Direct-hotspot regression coverage: Android `HotspotNetworkTest` covers local-only/no-internet networks, hotspot plus upstream Wi-Fi/cellular, changing subnets, API 29/34 source-address fallback, VPN preservation, subnet matching and bounded endpoint ranking. `ConnectionTest` verifies cancellation of stale in-flight candidates and replacement of an existing LAN endpoint received over authenticated Bluetooth, while leaving a still-advertised endpoint alone. Rust LAN tests cover interface prioritization, IPv4/IPv6 address matching and retiring only sessions whose local IP disappears. The systemd unit includes `AF_NETLINK`, verified with a temporary user-service socket probe. LAN/RFCOMM integration suites exercise authenticated address updates and concurrent files/audio/screens. See [direct-hotspot setup](direct-hotspot.md).

On 1 November 2026, the real laptop joined the paired SM-M356B's hotspot and retained Bluetooth. The fixed daemon advertised its hotspot address correctly. Testing exposed the stale router-side TCP session and produced the LAN-session retirement and companion endpoint-replacement fixes. The phone's pre-update companion did not establish the replacement hotspot LAN connection, so full physical hotspot validation remains pending installation of Preview 0.1.36. Its signed 4,674,905-byte APK was delivered successfully to the phone's Downloads/Unity folder over the restored home LAN. Both hotspot tests restored the previous laptop Wi-Fi connection. The final builds passed 155 Android tests and lint, the Rust workspace tests and clippy, and authenticated discovery/dual-transport integration tests.

Desktop menu coverage: `dbus-run-session -- python3 tests/desktop_integration_ui.py`, with a native Wayland or X11 GTK display, checks actual `org.gtk.Menus` and `org.gtk.Actions` exports, AppIndicator registration with a fake host, the D-Bus popup layout/properties/events, live Find Phone/Stop Ringing, selected-device routing, stale popup IDs, permission revocation, disconnect, close/reopen, host disappearance/restart and Quit cleanup. It uses isolated phone fixtures and a private session bus. Broadway does not export GTK application menus; use a native backend for this test. Existing call-popup and GTK smoke checks cover window lifetime and native layouts.

Expanded menu checks compare the complete native and indicator action/target sets, exercise direct playback, volume/mute, ringer, exact Bluetooth-device and hotspot requests, audio transport/start/stop, screen modes, real link-dialog buttons and stale-dialog rejection. They verify feature switches through both D-Bus action-state changes and indicator events, plus appearance/status/close-to-tray synchronization and saved preference reloads. These tests and the audio chooser test use temporary configuration directories so fixture choices cannot alter desktop preferences. Phone actions run against fixtures rather than physical devices.

Connectivity coverage: `tests/samsung_routines_integration.py` verifies real D-Bus/TLS phone device reports, observed radio/device changes, all routine actions, address targeting, unconfirmed results, malformed/duplicate-device rejection, local policy and remote permission/capability changes. `tests/phone_connectivity_ui.py` checks real GTK Mobile Hotspot and device switches, state-update feedback, stale rows and permission/disconnection clearing; `tests/samsung_routines_ui.py` covers the legacy buttons in their new Connectivity tab. Android `PhoneConnectivityTest` and `SamsungRoutinesTest` exercise actual public radio/profile APIs with isolated devices, opt-in, profile/BLE deduplication, ACL updates, phone-to-desktop events, permission revocation, exact-target validation, bounded notifications and replay protection. See [Connectivity setup](connectivity.md); physical Samsung execution and the Windows build require device/platform validation.

`tests/public_wifi_integration.py` runs against an isolated daemon and BlueZ fixture. It verifies that LAN and RFCOMM address updates require paired proof, TLS 1.2/plaintext are rejected, legacy clients remain compatible, and the daemon owns no UDP discovery socket. Rust tests cover CGNAT/public subnet boundaries, IPv6 listening and existing-port collisions. Android `PublicWifiTest` covers mobile-default Wi-Fi routing, preserving VPNs, authenticated endpoint validation/recovery, missing/stale manual addresses, saved public/private answers across reconnects/restarts/roaming, redacted identities, permission promotion, reused network handles and the real public/private choice dialog.

Run `source scripts/env.sh` and `scripts/test.sh` from a normal development environment. Network is needed only when dependencies are not cached. In a restricted sandbox, actual D-Bus, TCP, desktop rendering, Gradle lock sockets and ADB inspection require permission to access local sockets.

- Rust unit tests validate protocol identity/version bounds, cross-language hello fixture, device/session-bound HMAC and an independently computed fixed vector, framing limits and interrupted header/payload resumption, transfer integrity/path validation, bulk transport selection, bounded backoff, all 23 feature descriptors, and rejection of unsupported actions.
- `tests/integration.py`, under `dbus-run-session`, starts the actual daemon and the actual CLI, establishes TLS 1.3 over loopback, verifies the certificate pin, pairs a test peer through an explicit CLI approval, and tests authorization, two client connections, live events, bounded photo preview results and private operation access, media artwork metadata, selected SMS conversation requests, streamed file bytes in both directions, persistence, restart, wrong credentials, and revocation. The peer is strictly a test fixture, never a production UI data source.
- `tests/audio_integration.py`, under `dbus-run-session`, tests actual daemon/CLI D-Bus and a separate pinned TLS PCM stream using isolated fake `pactl`/`parec` executables. It verifies PCM integrity, token scope/replay rejection, cancellation, startup failure, output restoration, feature disable, replacement sessions, revocation and crash recovery without changing desktop audio. Physical phone latency remains unmeasured.
- `tests/architecture.py` checks the daemon dependency graph, frontend API-only communication, independent service, staged installation, and frontend removal without changing daemon binaries/service/CLI.
- `tests/launcher.py`, under `dbus-run-session`, installs the actual binaries into a temporary prefix and substitutes an explicit test-only D-Bus client for the fixed GTK script. It verifies automatic approval of the launched child, refusal of an unrelated client with the same label, scope expansion, revocation surviving unrelated signals, reapproval after daemon restart, a fresh grant after reopening, and continued daemon operation after closing the client. No fixture path is accepted by the production launcher.

Battery tests cover sensor units/signs, smoothed runtime, Android charging estimates, missing/invalid sensors, measured trends, history resets, periodic sampling and disconnect cleanup. File tests exercise verified Downloads publication, empty files, Unicode/unknown extensions, bad hashes, write-failure cleanup and exact bytes from a one-shot document provider. - `tests/gtk_smoke.py` renders the actual nine-page adaptive GTK client with explicitly isolated test fixtures in a separate application. It checks authorization gating before private snapshots, the friendly access prompt, control disabling on revocation, seventeen wide/narrow/light/dark layouts including Calls with separate output/microphone selectors, waiting and mute state, selected files and battery percentage/watts, charging and missing-sensor states, older companion notices, artwork/gallery rendering, font-scaled navigation breakpoints, and clearing private data on disconnect. Run with `GSETTINGS_BACKEND=memory GSK_RENDERER=cairo`. Captures are `/tmp/unity-refined-*.png`. The GUI has no production demo device or seeded fake phone state.
- `dbus-run-session -- python3 tests/file_transfer_ui.py`, with a GTK display available, exercises actual Gdk.FileList drop signals on all nine pages and another Unity window, multiple files and duplicate drops, symlink resolution, invalid/remote/oversized files, the public Transfer1.SendFile API, acknowledgements, retry selection, disconnects and disabled features. A temporary Broadway display can run this behavioral check without showing windows on the desktop.

The checked-in feature matrix distinguishes Linux protocol tests from Android hardware testing. Automated feature tests use an isolated TLS test peer. A paired phone was observed connected via LAN, but notification listener behavior, real SMS/carrier outcomes, SAF/MediaStore grants, MediaSession app behavior, DND/OEM policy, IME focus, accessibility gestures, battery reporting and long-term reconnect have not been validated end to end on Android hardware. Closing the GUI and removing its files are covered independently from those hardware limitations.

The installed native launcher and real GTK client were checked on Fedora with a paired SM-M356B: opening the app grants its fresh connection without a manual authorize command; the running client regains access after a daemon restart; quitting through the normal application action releases its registration; reopening receives a new grant while the daemon stays running. GTK exposes the normal quit action through Ctrl+Q and handles session-manager SIGTERM through its main loop.

Before distribution, test at least two physical Android versions, narrow and desktop GTK windows, suspend/resume, Bluetooth and Wi-Fi toggles, permission revocation, Android service termination, simultaneous devices, interrupted file transfers, malformed frames, a full transfer disk, stale document tokens, and changed TLS pins. Run device tests with carrier-aware consent before sending SMS. Do not declare a feature working merely because it compiles.

Known product gaps are in `features.md`: BLE transport, physical HFP/carrier call validation, direct MMS/RCS, desktop automatic clipboard integration, full photo-library pagination, and negotiated internet sharing. Phone notifications/SMS and received files, links and text have native desktop alerts. The operation history is capped and in memory; metadata/trust persists but phone contents and completed operations are cleared across daemon restarts.
