# Security and permissions

Pairing is closed by default and explicitly opens for at most 120 seconds. Phone approval expires after 90 seconds. Copy and compare the full Linux TLS certificate fingerprint using a trusted physical or other out-of-band channel; a LAN discovery packet is not authenticated. Never silently accept a changed fingerprint. Android verifies the pin and certificate validity inside the TLS handshake before sending hello, proof, or feature data.

The daemon generates its certificate using rcgen and serves TLS using rustls/ring. Android uses platform TLS 1.3 and standard HMAC-SHA256. Per-phone credentials are 256-bit random secrets. Authentication proofs are bound to both the phone ID and a random per-session challenge, and verified in constant time. TLS authenticates records and sequences; early data is disabled. A captured proof cannot authenticate a different device or a later session. This is pinned TLS plus device challenge authentication, not mutual X.509 client-certificate TLS. All future transports must authenticate the same device credential before carrying feature traffic; BLE is intentionally unavailable until this exists.

Linux stores its identity, key, trust, and policy under `$XDG_STATE_HOME/unity` or `~/.local/state/unity`. The directory must be owned by the daemon user, must enforce mode 0700, and credential files require 0600. Atomic writes use a new private temporary file, fsync, and rename. Android wraps its pairing secret using an Android Keystore AES-GCM key; the app disables backup. Credentials are never included in diagnostics, D-Bus properties, or logs. The daemon does not store phone passwords. Identity loss requires fresh pairing.

D-Bus unique names identify clients. Sensitive methods require per-connection read/control grants. Only the trusted CLI executable colocated with the daemon can approve grants. The daemon checks the bus-reported Unix UID/PID, resolves `/proc/PID/exe`, and verifies executable ownership and write permissions. Grant cleanup listens for `NameOwnerChanged`; secrets never appear in broadcast signals. Public device name/ID/capabilities remain discoverable within the session. `read` is a broad content grant, and `control` includes sensitive SMS/actions; users should approve only clients they trust.

Launching installed Unity explicitly starts `unityctl launch-gtk`, which launches the fixed `share/unity/unity.py` script with `/usr/bin/python3`. The script must be a regular, non-symlink file owned by the current user or root and not writable by other users. The CLI approves only requests whose bus-reported PID and UID match its live child, and only read/control scopes. It does not trust client labels, executable names, or all Python processes. Approval is connection-scoped; a live launched child can regain it after daemon restart. Revocation is not reversed by unrelated access requests or device state signals. An explicit new request by the launched child can request access again. Directly running the Python frontend provides an Allow access dialog that invokes the trusted CLI only after confirmation. Third-party clients continue to require explicit CLI approval. `GetAccessStatus` reveals only the calling connection's status; expanding a grant's scopes requires fresh approval.

**Boundary:** ordinary session-bus access does not automatically grant private contents. Fully malicious unsandboxed code running as the same Unix user can still read that user's private files, manipulate their binaries, or inspect their processes. This implementation is not a security boundary against such code or root. Stronger per-application isolation requires Flatpak/portal identities or a separate security domain. Never suggest that Unix file modes alone prevent same-user attackers.

Input validation includes bounded messages, per-feature command fields, numeric ranges, safe URL schemes, regular-file checks with `O_NOFOLLOW`, fixed transfer quarantine roots, size/hash verification, and opaque Android document/photo tokens. A received filename is never interpreted as a path. Files are not executed or automatically opened. Intermediate files are removed on disconnect and on integrity failure. No root daemon, shell execution of peer data, or automatic firewall mutation is used.

## Android consent and restrictions

Sensitive features default to disabled. Feature toggles, OS permissions, current service availability, and Linux-local toggles are rechecked independently. Runtime capability changes clear now-unavailable cached feature state.

- Notifications use the explicitly enabled [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService). Reply uses RemoteInput and the original action PendingIntent. Only advertised actions are accepted. Android or the source app can redact or block sensitive contents/actions. Excluded apps are configured on the phone; there is no desktop per-app preferences editor yet.
- SMS uses granted READ_SMS/SEND_SMS and SmsManager. The OS, installer, OEM, and store distribution policy may restrict access. This app is not a complete default SMS handler; see [Android default-handler guidance](https://developer.android.com/guide/topics/permissions/default-handlers). Sending acknowledges submission to the modem, not delivery or success of the carrier transaction. No SMS permissions are automatically granted.
- Calls use phone-state broadcasts after READ_PHONE_STATE consent. Caller identity can be empty. Answer/hangup are unavailable until a complete supported dialer/InCallService integration exists; BLE is not a telephony profile.
- Clipboard sharing is explicit while the app is foreground. Incoming text requires a tap to apply. Background automatic phone clipboard reading is not advertised.
- Remote files are confined to a user-selected, persisted Storage Access Framework tree. Photos use MediaStore and the actual granted full/selected photo scope. Tokens cannot name arbitrary content provider URIs. Received files remain in private app storage; Android's file viewer/export UX remains unfinished.
- Media uses active MediaSession controllers via notification-listener authorization, checks supported playback actions, and listens for metadata/state changes. It does not route call or media audio.
- Ringer/DND requires notification-policy access and uses AudioManager/NotificationManager. Android versions may scope interruption-policy changes. Find-phone plays the alarm ringtone for at most 30 seconds and does not change the user's volume settings.
- Remote typing requires the selected Unity IME and a focused field. Remote touch requires explicit AccessibilityService enablement and uses bounded tap/swipe gestures. The accessibility service does not retrieve window contents.
- Screen mirroring is unavailable. A future implementation must use [MediaProjection](https://developer.android.com/media/grow/media-projection), per-session user consent, a suitable foreground service, bounded encoding, and a Linux decoder. Do not reuse expired capture tokens or claim unrestricted capture.
- Hotspot commands post a phone review notification and open wireless settings. They do not enable tethering or report that internet is shared. [Local-only hotspot](https://developer.android.com/reference/android/net/wifi/WifiManager) is not internet tethering; adapter concurrency and Wi-Fi Direct availability must be detected before implementing any new networking flow.

The Android foreground service is visible and uses the connected-device service type. Android/OEM background policy can still terminate it or restrict restoration. There is no persistent wake lock. Hardware suspend/resume and OEM-specific lifecycle behavior require device testing.

Photo previews and media artwork are private phone contents, covered by the same connection-scoped read/control grants as other feature data. Previews use at most 320×320 pixels and 32 KiB of JPEG bytes. Linux validates JPEG frame dimensions against the declared dimensions before exposing bytes to clients. GTK keeps textures in session memory, clears them on disconnect, and never downloads artwork URLs. Android accepts local bitmap or accessible content-URI artwork, with no remote URL retrieval. Original photos use the existing explicit, integrity-checked file transfer.
