# Laptop audio on phone

Install the updated Linux daemon/GTK client and Android companion 0.1.3 or later. On Android, enable **Features → Media → Laptop audio on phone**. Connect on the same LAN. On Linux, open **Media** and select **Play laptop audio on this phone**. Turn it off to restore the laptop speakers. The phone's normal media volume and selected output (speaker, wired headphones, or Bluetooth) apply. Wired headphones or the phone speaker avoid Bluetooth's additional delay.

Linux requires `pactl` and `parec` from `pulseaudio-utils`, with PipeWire-Pulse or PulseAudio running in the user's session. No root privileges or additional listening port are needed. Audio routing is independent of the phone media-controls/notification-access permission. Only one phone can receive laptop audio at a time, and routing must be selected again after reconnecting.

Selecting the option creates a temporary null sink, makes it the laptop's default output, moves existing application playback streams there, and records its monitor. This redirects laptop playback rather than playing it from both devices. Apps that explicitly select a different output after routing starts can bypass the default; select **Unity Phone** in their audio output settings. Microphone recording and phone call audio are outside this feature.

The daemon remembers original output devices for existing streams. New streams return to the prior default. If the user changes the default output while routing is active, that selection is preserved when routing stops. If the original output is unplugged, restoration uses another available output. A private `audio-route.json` journal enables recovery after a daemon crash or restart. A failed restoration retains the journal for retry and reports an error.

The data path uses a separate pinned TLS 1.3 connection over the selected transport (the existing TCP port on LAN, or the dedicated audio RFCOMM UUID on Bluetooth), authorized by a random, one-use token delivered through the paired control session. The token expires after ten seconds, is bound to the device and control-session generation, and cannot replace a control session. Disconnection of that parent link, unpairing, either side disabling audio, cancellation, capture failure, audio focus loss, and normal daemon/service shutdown stop the route and restore laptop output.

Audio is stereo signed 16-bit little-endian PCM at 48 kHz, in 480-frame (10 ms) packets. After a framed JSON `ready`, each packet is an unsigned 64-bit big-endian sequence number followed by exactly 1,920 PCM bytes. No JSON/base64 or audio codec runs per packet. PCM payload bandwidth is 192,000 bytes/s (1.536 Mb/s), plus TLS/TCP overhead. Uncompressed audio trades LAN bandwidth for low CPU cost and no codec delay.

Capture requests 10 ms latency with 5 ms processing intervals. Linux keeps only the latest capture packet, limits the TCP send buffer, disables Nagle, and stops a write stalled for 100 ms. Android uses a three-packet queue, drops old packets, flushes after sequence gaps, requests a 20 ms AudioTrack buffer and low-latency performance mode, and runs playback at audio thread priority. These are requested buffer limits, not measured end-to-end latency: device minimums, Wi-Fi jitter/retransmission, sample-rate conversion, Android scheduling, and the selected phone output still affect delay. Hardware latency has not been measured.

The isolated audio integration test exercises actual D-Bus and TLS with test-only sound tools: PCM integrity, wrong/replayed tokens, capability gating, one active route, startup failure, cancellation, output restoration, revocation, replacement sessions, and crash recovery. Android tests cover fixed-format validation, fragmented PCM reads, malformed/truncated packets, and default-off UI consent. These tests do not substitute for physical phone playback and latency measurements.

Implementation references: [Android AudioTrack](https://developer.android.com/reference/android/media/AudioTrack), [AudioTrack low-latency builder](https://developer.android.com/reference/android/media/AudioTrack.Builder#setPerformanceMode(int)), [Android audio focus](https://developer.android.com/media/optimize/audio-focus), [PipeWire null sink](https://docs.pipewire.org/page_pulse_module_null_sink.html), and [PulseAudio capture implementation](https://github.com/pulseaudio/pulseaudio/blob/master/src/utils/pacat.c).

In the combined mode, audio prefers LAN while Bluetooth remains available for controls. Joining, reconnecting or losing the Bluetooth link leaves a LAN audio stream running. Streams retain their original endpoint and token; loss of that endpoint stops/restores the route, and a new start uses the remaining connection.
