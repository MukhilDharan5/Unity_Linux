# Campus and public Wi-Fi

Update both apps to companion Preview 0.1.25 and the matching Linux build. Keep **Connection method → Bluetooth + Wi-Fi / LAN** selected. Pair Bluetooth in the system settings and verify the computer's full TLS fingerprint in Unity. The paired Bluetooth connection now supplies the computer's current Wi-Fi addresses and listening ports privately. A saved home address can remain as a fallback; it no longer prevents connecting at college. Both transports stay connected and reconnect independently.

Unity accepts shared campus IPv4 addresses in `100.64.0.0/10`, directly connected public IPv4/IPv6 subnets, and the existing private LAN ranges. The default Linux listener supports IPv4 and IPv6 at TCP 17161. It also selects one unused TCP port from 1714–1764, starting at 1764, to work with existing LAN-companion firewall allowances. An existing listener is never replaced, and Unity does not change firewall rules. The encrypted address update advertises the actual selected port. Explicit custom bind addresses and ports retain their configured listener without the companion-port fallback.

Android binds each LAN socket and its audio/screen streams to the Wi-Fi or Ethernet network, even if mobile data remains the default while Wi-Fi sign-in is pending. An active VPN remains respected. Network changes reconnect only the affected link. **Settings → Network privacy** shows the active endpoint or the Wi-Fi error; a working Bluetooth connection no longer conceals a LAN failure. Open Android Wi-Fi settings to complete any sign-in.

All application data uses pinned TLS 1.3 over Wi-Fi and Bluetooth, including files, controls, pairing credentials, audio, screen frames and address updates. There is no plaintext UDP discovery listener or broadcast. The manual fingerprint comparison and explicit local approval are still required for first pairing. Legacy companions can still connect without requesting address updates.

Open/enhanced-open Wi-Fi and captive portals are treated as suspected public networks. When Android cannot establish network trust, Unity asks **Is this Wi-Fi public or private?**, with Public/shared selected by default. Companion **0.1.30** saves either answer per Wi-Fi profile across reconnects, access-point roaming and app/service restarts. **Settings → Network privacy → Review current Wi-Fi** changes a saved answer. Not now defers that connection's question. Encryption stays enabled for every answer, including private and deferred.

Android requires **Location → Precise → While using the app** and the system Location setting to expose the connected Wi-Fi name. Unity asks when saving a choice; it does not scan for networks, obtain coordinates or request background location. Only a device-salted SHA-256 hash of the SSID and security type is stored in private app preferences, alongside the choice. The raw name, BSSID and location are not saved or sent to the laptop. Without access to the name, the choice still applies to that connection, but Unity explains that it cannot recognize the Wi-Fi after reconnecting. Android documents this requirement under [WifiInfo](https://developer.android.com/reference/kotlin/android/net/wifi/WifiInfo.html).

A remembered profile is a convenience for the user's classification, not proof of the access point's identity: another access point can reuse a Wi-Fi name and security type. Pairing pins and verified TLS 1.3 remain required on every network.

Routers that actually block all communication between clients still require a network route that permits peers, such as a different Wi-Fi or a user-managed VPN; encryption does not bypass client isolation. Bluetooth continues independently. The college network itself has not been physically tested. Automated tests cover campus address acceptance, mobile-default routing, VPN preservation, encrypted address updates over LAN/RFCOMM, authentication and TLS downgrade rejection, privacy choices and independent reconnects.
