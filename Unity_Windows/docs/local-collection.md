# Optional local device collection

Open **Settings → Local device data → Collect local device data**. The setting starts off. Enabling it opens a description of the collected categories, local storage, usage definition and retention; **Allow collection** is required before any new collection source opens. Cancel leaves collection off. Preview mode disables the switch and never starts this collector.

This implements the Windows portion of the supplied **Unity Companion App: Data Requirements v2.0 (25 October 2026)**. It collects only the PC's own record (`device_id: laptop`), independently of pairing and phone permissions. Android and Linux are unchanged.

## Local handling and consent

- No upload, phone message, dashboard integration, network listener, HTTP request, ping, speed test or Wi-Fi scan is added. The collector has no reference to the host or a device session. Passive interface counters measure local interface traffic, not connection speed.
- Approval is saved in `%LOCALAPPDATA%/UnityWindows/local-collection-consent.json`, with consent/schema versions, approval time and a stable app-assigned random device UID. Missing, damaged or incompatible approval fails closed. An enabled setting resumes when Unity next starts; it does not add Windows auto-start.
- Records are saved to the readable UTF-8 file **`%LOCALAPPDATA%/UnityWindows/local-collection.csv`**. The exact path is shown in Settings. A first sample is written after approval, followed by a poll every **5 seconds**, including usage readings. CSV writes replace the file atomically so readers never see a partly appended row. No collected values are written to `unity.log`.
- The CSV retains a **rolling 30-minute window**, bounded to 361 samples including the exact cutoff boundary. Older rows are removed on each write and by a separate five-second cleanup timer, even if a native poll is blocked or fails. Expired rows are pruned again on approved startup. Cleanup retries after a temporary file lock. Abandoned CSV temporary files and the previous encrypted `local-collection.dat` checkpoint are removed; there is no separate persistent usage/history store.
- A temporary reader/file lock does not stop polling. Settings reports the write failure while bounded pending samples remain in memory; saving and cleanup retry every five seconds. Once the lock is released, only samples still inside the retention window are written.
- Closing Unity to the notification area keeps approved collection and cleanup running. **Quit Unity** stops both and releases the native handles/events. While Unity is quit there is no background cleanup process; the remaining CSV is pruned when collection next starts. Turning the switch off cancels pending reads, clears the in-memory snapshot and deletes the CSV and temporary files; the disabled preference and stable UID remain. Storage failures are reported in Settings.
- Windows privacy restrictions are respected. The collector does not request or grant extra OS permissions. Denied fields stay unavailable. It records app names and active durations, not window titles, keystrokes, screen images, audio, notification bodies or process executable paths. App IDs are hashes of executable identity; exact app names are retained in structured usage.

## Data contract and available sources

Every CSV record includes the 16 core columns in their canonical order, followed by live metadata and all 61 optional telemetry fields. Schema `2.0`, UTC capture time, unique sample ID, device UID, source IANA timezone, `is_demo: false`, availability metadata and a `field_status` map are preserved. Structured `app_usage` and `field_status` values are JSON inside properly quoted CSV cells. Unavailable metrics have empty cells and explicit statuses; known empty text, zero and false retain their meaning through those statuses. Numbers use invariant decimal points. Commas, quotes, Unicode and embedded line breaks round-trip without changing source names. Static hardware and cached timeline readings keep their original observation times.

This is a timestamped history CSV with additional columns, rather than the dashboard's legacy one-current-row-per-device CSV. No dashboard consumer is connected by this change. A future consumer must use the metadata/status columns to interpret empty cells and select the desired sample.

| Category | Windows source and behavior |
| --- | --- |
| Identity and hardware | Computer name; CPU registry model; Windows processor topology; OS-reported usable physical memory; SMBIOS memory technology and configured transfer rate where the SMBIOS version specifies MT/s; Windows version/build registry and native version APIs. Hardware is read once per collection session. |
| Power | Actual effective Windows power overlay or active plan; `GetSystemPowerStatus` for battery presence, external power, charge and estimated runtime; read-only battery driver queries for charging/discharging/full/not-charging state, health ratio, cycle count, voltage, temperature and absolute battery power where provided. Relative rates and unknown sentinels stay null. Single-battery sensor/rate readings are withheld on multi-battery systems. Power is labeled `battery_charge` or `battery_discharge`, never charger input or whole-system consumption. Driver capacities in mWh are not mislabeled mAh. |
| Network | Windows-selected internet connection profile and its matching adapter; actual transport, SSID/interface label and radio quality; Native Wi-Fi generation, link rates, channel, RSSI and single-link frequency where available; passive interface-byte-counter throughput with the observation window in its source. Offline has no fabricated name/signal; Ethernet has no radio signal. |
| Media and audio | Read-only Windows GSMTC sessions, preferring playing sessions and then the most recently observed activity/timeline update. Title, artist, app ID and playback state belong to one session. Cached timeline timestamps are preserved; unknown/live duration stays null. No session is distinct from denied access. Core Audio supplies the actual default multimedia output label and volume. |
| Usage and unlocks | Foreground/session/display/idle sampling every five seconds, with each CSV poll. Current-session WTS lock state, session display-power notifications and `GetLastInputInfo` exclude locked, display-off and idle periods (60-second idle cutoff). Both interval endpoints must be active; sampling/suspend gaps over seven seconds are discarded. One interval goes to one app. Only observed locked-to-unlocked transitions count as unlocks; transitions entirely between polls are not reconstructed. |

Core and usage snapshots target five seconds while Unity runs. Slow reads delay a poll; coalesced timer ticks cannot cause extra native polls within five seconds or fabricate missed samples. Cleanup runs independently of native polling. Field times remain honest when Windows delays a read. A future consumer must calculate device/field staleness from those timestamps; this change does not add a dashboard or stale-state renderer.

Usage starts at approval, uses the PC's local date and timezone, and never reconstructs earlier activity. Running daily counters stay in memory and restart with Unity; the file does not hide older aggregate checkpoints alongside its 30-minute sample history. Coverage identifies the actual session start and gaps. The 30-minute limit applies to snapshot rows; a current row can contain the current session's daily cumulative usage. Minutes are floored; app minutes cannot exceed total minutes. Legacy app text merges duplicate names and omits names containing `:`/`;`, while `app_usage` preserves the exact names and stable IDs. Yesterday and seven-day averages are populated only if complete prior local days were observed in the same uninterrupted Unity session using the same method/timezone; missing days are not zero.

Windows does not expose a trustworthy public query for its actual Windows 11 **Do Not Disturb** switch; notification suppression and Focus activity are not substituted for it. That core key is present with `unsupported` status. Vendor-only temperatures/fans, charger protocol/input and mAh capacities, calibrated listening levels, stream codecs, noise cancellation/spatial audio, complete notification history, pickup events, patch dates and undefined focus windows also remain null unless a supported source is implemented. Optional unavailability never blocks the remaining readings. Latency is unavailable because collection makes no outgoing probe.

## Verification

The deterministic collector tests use fixture sources and an injected clock. They do not grant real consent or read this computer's hardware, network names, media or app activity. Tests cover default-off/no source construction, versioned saved approval, restart identity, five-second core/usage cadence and original hardware timestamps, CSV columns and quoting, Unicode and mixed newline styles, invariant numbers, structured values/statuses, cancellation/deletion, exact retention boundaries, startup pruning, cleanup during blocked reads, temporary file locks, legacy-checkpoint removal, source-local days, idle/lock/display/suspend exclusion, app attribution/names, coverage, complete-day baselines and native battery conversions/sentinels. Native entry-point checks resolve symbols without invoking collection APIs.

Run just these tests after building the test project:

```powershell
dotnet tests/Unity.Tests/bin/Debug/net10.0-windows10.0.26100.0/Unity.Tests.dll --telemetry-only
```

Actual sensor availability, Windows location/media access restrictions, display/lock transitions and long-running day-boundary behavior still need user-approved physical validation. Do not enable real collection as an automated test or copy a fixture approval into the user's normal profile.
