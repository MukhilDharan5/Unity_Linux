# Security and permissions

Pairing is closed by default and explicitly opens for at most 120 seconds. Phone approval expires after 90 seconds. Copy and compare the full Linux TLS certificate fingerprint using a trusted physical or other out-of-band channel; network addresses do not prove identity. Plaintext UDP discovery is removed; paired address updates travel inside TLS. Never silently accept a changed fingerprint. Android verifies the pin and certificate validity inside the TLS handshake before sending hello, proof, or feature data.

The daemon generates its certificate using rcgen and serves TLS using rustls/ring. Android uses platform TLS 1.3 and standard HMAC-SHA256. Per-phone credentials are 256-bit random secrets. Authentication proofs are bound to both the phone ID and a random per-session challenge, and verified in constant time. TLS authenticates records and sequences; early data is disabled. A captured proof cannot authenticate a different device or a later session. This is pinned TLS plus device challenge authentication, not mutual X.509 client-certificate TLS. LAN and Bluetooth RFCOMM authenticate the same device credential before feature traffic. Bluetooth bonding is followed by pinned TLS 1.3 and Unity approval / challenge authentication. BlueZ descriptors are accepted only from the registered service owner; separate audio/screen profiles require existing session-bound one-use tokens. See [Bluetooth](bluetooth.md).

Linux stores its identity, key, trust, and policy under `$XDG_STATE_HOME/unity` or `~/.local/state/unity`. The directory must be owned by the daemon user, must enforce mode 0700, and credential files require 0600. Atomic writes use a new private temporary file, fsync, and rename. Android wraps its pairing secret using an Android Keystore AES-GCM key; the app disables backup. Credentials are never included in diagnostics, D-Bus properties, or logs. The daemon does not store phone passwords. Identity loss requires fresh pairing.

D-Bus unique names identify clients. Sensitive methods require per-connection read/control grants. Only the trusted CLI executable colocated with the daemon can approve grants. The daemon checks the bus-reported Unix UID/PID, resolves `/proc/PID/exe`, and verifies executable ownership and write permissions. Grant cleanup listens for `NameOwnerChanged`; secrets never appear in broadcast signals. Public device name/ID/capabilities remain discoverable within the session. `read` is a broad content grant, and `control` includes sensitive SMS/actions; users should approve only clients they trust.

Launching installed Unity explicitly starts `unityctl launch-gtk`, which launches the fixed `share/unity/unity.py` script with `/usr/bin/python3`. The script must be a regular, non-symlink file owned by the current user or root and not writable by other users. The CLI approves only requests whose bus-reported PID and UID match its live child, and only read/control scopes. It does not trust client labels, executable names, or all Python processes. Approval is connection-scoped; a live launched child can regain it after daemon restart. Revocation is not reversed by unrelated access requests or device state signals. An explicit new request by the launched child can request access again. Directly running the Python frontend provides an Allow access dialog that invokes the trusted CLI only after confirmation. Third-party clients continue to require explicit CLI approval. `GetAccessStatus` reveals only the calling connection's status; expanding a grant's scopes requires fresh approval.

**Boundary:** ordinary session-bus access does not automatically grant private contents. Fully malicious unsandboxed code running as the same Unix user can still read that user's private files, manipulate their binaries, or inspect their processes. This implementation is not a security boundary against such code or root. Stronger per-application isolation requires Flatpak/portal identities or a separate security domain. Never suggest that Unix file modes alone prevent same-user attackers.

Input validation includes bounded messages, per-feature command fields, numeric ranges, safe URL schemes, regular-file checks with `O_NOFOLLOW`, fixed transfer quarantine roots, size/hash verification, and opaque Android document/photo tokens. A received filename is never interpreted as a path. Files are not executed or automatically opened. Intermediate files are removed on disconnect and on integrity failure. No root daemon, shell execution of peer data, or automatic firewall mutation is used.

[Receipt notifications](received-items.md) contain explicit user-click actions. Linux accepts notification signals only from the current service owner, clears retained actions on server restart, escapes markup, and opens received regular files through read-only portal descriptors. Shared text is saved with mode 0600 when opened. Android uses an unexported activity and immutable, distinct PendingIntents carrying the original item; file viewer intents grant read access only to the published MediaStore URI. Links are restricted to validated HTTP(S) addresses. Receipt notifications remain usable after a transport disconnect; only successfully published files produce alerts.

## Android consent and restrictions

Sensitive features default to disabled. Feature toggles, OS permissions, current service availability, and Linux-local toggles are rechecked independently. Runtime capability changes clear now-unavailable cached feature state.

- Notifications use the explicitly enabled [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService). Reply uses RemoteInput and the original action PendingIntent. Only advertised actions are accepted. Android or the source app can redact or block sensitive contents/actions. Excluded apps are configured on the phone; there is no desktop per-app preferences editor yet.
- SMS uses granted READ_SMS/SEND_SMS and SmsManager. The OS, installer, OEM, and store distribution policy may restrict access. This app is not a complete default SMS handler; see [Android default-handler guidance](https://developer.android.com/guide/topics/permissions/default-handlers). Sending first acknowledges modem submission; multipart sent/delivery callbacks report later carrier outcomes, with unconfirmed delivery when no receipt arrives. No SMS permissions are automatically granted.
- Call management is default-off and uses ordinary Android CALL_PHONE/READ_PHONE_STATE permissions for companion dialing and an explicitly selected Linux oFono HFP phone for live call control. HFP mode needs no default-dialer role or special ongoing-call permission. Phone speakerphone routing is an explicit opt-in to the default Phone role; its InCallService is protected by Android BIND_INCALL_SERVICE and local call UI works independently of the companion connection. Remote native controls recheck opt-in, ordinary permissions, current role, call identity and call state. The desktop popup uses the installed launcher’s existing verified process grant. Contacts and call history require separate permissions. Call IDs prevent stale controls from affecting another call. Native desktop notification actions recheck device policy and use the current notification-service owner. Computer microphone/speaker loopbacks exist only for an active call transferred to Bluetooth, with private recovery journals and owned-module cleanup. BLE is not a telephony profile. See [telephony](telephony.md).
- Clipboard text sync starts enabled on Android and respects explicit feature disables on either device. Incoming text is applied automatically. Android background reads can use an explicitly authorized Shizuku user service; a foreground service alone does not grant that access. The helper exposes only clipboard reads/listeners, verifies its app caller UID, stops when sharing or the connection stops, and does not persist text. Unity keeps the current keyboard. See [clipboard setup](clipboard-sync.md).
- Remote files are confined to a user-selected, persisted Storage Access Framework tree. Photos use MediaStore and the actual granted full/selected photo scope. Tokens cannot name arbitrary content provider URIs. Companion 0.1.5+ publishes verified received files in Downloads/Unity; 0.1.9 opens the saved file from its receipt notification with a read-only grant. Older companions retain files in private app storage.
- Media uses active MediaSession controllers via notification-listener authorization, checks supported playback actions, and listens for metadata/state changes. Phone cellular audio uses the separate consent-based Bluetooth HFP call route; it is not exposed to Android PCM capture. The separate default-off audio feature plays laptop PCM after a session-bound, one-use TLS stream token, with Android audio-focus handling and explicit desktop routing selection.
- Ringer/DND requires notification-policy access and uses AudioManager/NotificationManager. Android versions may scope interruption-policy changes. Find-phone plays the alarm ringtone for at most 30 seconds and does not change the user's volume settings.
- Remote typing requires the selected Unity IME and a focused field. Remote touch requires explicit AccessibilityService enablement and uses bounded tap/swipe gestures. The accessibility service does not retrieve window contents.
- Screen sharing uses default-off opt-in, per-session MediaProjection or desktop portal approval, bounded JPEG capture/decoding and a separate pinned TLS channel with single-use tokens bound to the paired session. Android adds the media-projection foreground type before obtaining the approved projection; rotation reuses the existing display. Stop/disable/disconnect/revocation discard frames and close capture resources. Screen pixels require D-Bus read grants; broadcast signals contain sequence metadata only.
- Remote device locking is default-off on the phone. Android requires explicit device-admin activation for force-lock only. Desktop requests are limited to lock and screen; local per-device policy gates both directions. Phone fingerprint approval for local PAM services is a separate, default-off feature with administrator enrollment and fresh biometric signatures; see [PAM authentication](phone-authentication.md). Remote lock commands do not grant authentication.
- Hotspot commands post a phone review notification and open wireless settings. They do not enable tethering or report that internet is shared. [Local-only hotspot](https://developer.android.com/reference/android/net/wifi/WifiManager) is not internet tethering; adapter concurrency and Wi-Fi Direct availability must be detected before implementing any new networking flow.
- The separate opt-in [Samsung Routines bridge](samsung-routines.md) accepts fixed hotspot/generic-disconnect actions and address-scoped device disconnects. Device disconnects require a valid address that is still reported connected on the phone. Samsung routines and their Bluetooth targets are configured locally on the phone. Posting requires Unity notification permission and an enabled trigger category. Results confirm only notification submission; normal authenticated command replay and desktop feature policy still apply.
- [Phone connectivity reports](connectivity.md) start off. They share hotspot state and bounded connected Bluetooth names, addresses and profiles only with the paired computer. Nearby devices permission gates Bluetooth metadata; denial clears the reported device list without blocking hotspot reporting. Merely paired devices are excluded, and incomplete public-API coverage is explicit.

The Android foreground service is visible and uses the connected-device service type, adding media-playback while laptop audio is active and media-projection while phone capture is active. Android/OEM background policy can still terminate it or restrict restoration. There is no persistent wake lock. Hardware suspend/resume and OEM-specific lifecycle behavior require device testing.

Photo previews and media artwork are private phone contents, covered by the same connection-scoped read/control grants as other feature data. Gallery previews use at most 320×320 pixels and 32 KiB of JPEG bytes. Negotiated media covers use up to 1024×1024 pixels and 192 KiB, with SHA-256 content references and bounded per-device caches. Linux validates JPEG frame dimensions against the declared dimensions before exposing bytes to clients. GTK keeps textures in session memory, clears them on disconnect, and never downloads artwork URLs. Artwork sources come from native player metadata: Android accepts bitmaps, accessible local/content URIs and bounded HTTPS image responses; Linux accepts bounded regular files and HTTP(S) image responses. Incoming paired metadata supplies validated image bytes, never a URL for the other client to fetch. Original photos use the existing explicit, integrity-checked file transfer.

Desktop screen input is restricted to the approved RemoteDesktop portal session, active paired generation, current screen session ID and bounded validated messages. Mouse coordinates are normalized within the shared monitor; pressed keys/buttons are released on shutdown. KDE unattended sharing uses a dedicated registered Unity application ID and an explicit permission-store grant. A temporary monitor mirrors the desktop, allowing the physical laptop panel to be disabled while remote input remains usable. A separate five-second display lease restores the panel on lost delivery or process exit, with a private recovery journal and startup recovery.

Enabled phone-native media is intentionally exported through desktop MPRIS so normal Now Playing clients can read metadata and control that phone session without a separate private Unity API grant. Exports require the paired phone’s live media capability and the desktop media toggle, disappear on disconnect/session end/opt-out, and reject stale-session/track controls. The exported service namespace and Unity DesktopEntry are excluded from laptop-native discovery. Cover images are validated, written under the private state directory with mode 0600, exposed as local file URIs and removed when no active export uses them. GTK gallery drags return only hash-verified original download paths correlated to the requesting device, link generation and operation; existing files are never overwritten when restoring original names.
